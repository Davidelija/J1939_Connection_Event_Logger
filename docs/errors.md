# Error-handling table

One row per expected error (decision X36). Claude Code builds to this table, every row gets a test using fault injection in the desktop platform layer (named by the requirement ID it verifies), and the user manual's troubleshooting table is generated from it. It starts in build step 1 and each step adds its rows. Seeded from the final design review, Nov 7, 2026.

The Test column names the test or fixture folder for each row as its build step lands; CI fails a release while any row still shows a placeholder.

Columns: **Operator** is what the operator should do, in plain words; `tools/troubleshooting.py` generates the user manual's troubleshooting table from this table (DC-22). **Kind** is the fault kind used in code and tests: `PlatformError.kind` takes its values from this column, and the desktop platform's fault plan and the fixture manifests' `faults` use them; this column is the single list. **Detection** is how the logger notices; **Action** is what it does; **Record** is what it writes (record type and cause); **Light** is the status light; **Transmit** is whether transmitting continues.
